設計ドキュメント — Autodesk 学習ガイド（MB / Maya）

このファイルは学習ガイド本体とは別に、AI再利用時の読み込み用として作成された設計メモです。
「なぜこう作ったか」「どういう基準でリソースを選んだか」「後で調整するときに何を変えればよいか」を記録しています。

1. プロジェクト概要

Autodesk の MotionBuilder（MB） と Maya を実務で使うための自習用 HTML 資料集。 ブラウザで開くスタンドアロンな静的 HTML であり、外部サーバー・フレームワーク不使用。

制約条件（設計判断に強く影響）

  • Autodesk 従量課金プランの最低量トークン。1日・ソフトごとの起動回数に上限あり、残り合計 15 回前後。
  • 1 回の勉強セッション = 4〜6 時間 が目安。
  • MB は仕事で使うため実践寄り。Maya は MB 経験者が入門する想定。
  • 資料はソフト起動前に読めるよう設計する（トークンを使わず事前学習）。

3. 教育フレームワーク — 「目的 → 機能 → 理屈」

ユーザーの学習スタイルの傾向として、「何のためにあるか → どの機能で達成するか → なぜその機能で達成できるか」 という構造で説明されると理解しやすい。これを全ページ共通の概念マップ（.concept-map）として実装している。

概念マップの構造（HTML）
<div class="concept-map">
  <!-- ヘッダー行 -->
  <div class="concept-row header">
    <div class="concept-cell goal">目的（何をしたい）</div>
    <div class="concept-arrow">→</div>
    <div class="concept-cell feature">機能（何を使う）</div>
    <div class="concept-arrow">→</div>
    <div class="concept-cell logic">理屈（なぜ効く）</div>
  </div>
  <!-- データ行 -->
  <div class="concept-row">
    <div class="concept-cell goal">...</div>
    ...
  </div>
</div>

各ページのトップに配置し、「この章で何を学ぶか」のマップとして機能させている。セクション内でも個別に挿入可能。

8. AI 再利用時のコンテキスト補足

ファイルを読み込んで調整作業をする場合のポイント
  • CSS は common.css を先に確認すること。コンポーネントのベーススタイルはそちらにある。
  • ページ固有スタイルは各 HTML の <style> タグ内に記述されている。
  • study_plan.html のみ ref-box 内のインデントが 4 スペース（他ファイルは 2 スペース）。Edit ツール使用時は既存インデントに合わせること。
  • 参考リンクのクラスは class="doc"（公式・青）/ class="ext"（外部・グリーン）/ class="yt"（YouTube・赤）の 3 種。アイコン絵文字もセットで使う（📄 / 📖 / ▶）。
  • 日本語を含む URL は パーセントエンコーディング済みの形で href に書くこと（ブラウザが解釈できるが、確実性のため）。
  • nav は全ファイルを更新する必要があるため、ページ追加・削除時は 9 ファイル全部を確認すること（next-link チェーンもセットで）。
  • 用語の初出管理：新しい専門用語を本文に書くときは、glossary.html に1行定義を追加し、初出箇所に <a class="term" href="glossary.html#用語id"> でリンクする。ページ内で説明済みの用語にリンクは不要。
  • 新ページの型：ページを追加するときは「冒頭に .prereq（前提ブロック）・区切りに .checkpoint・スクショ予定地に .fig-slot」の3点セットを踏襲する。

ユーザーの設計傾向（調整提案をする際に参考にする）

  • 「なぜこの機能があるのか（理屈）」を理解してから使いたい学習スタイル。
  • 図解・視覚的な構造整理を好む。テキスト説明だけより概念マップ・フロー図が有効。
  • 実務に直結する情報を優先。理論だけで終わらず「で、実際どう操作するか」まで含める。
  • トークン制約があるため、ソフト起動前に読める分量・構成にする。

9. 初心者向け再構成の記録（2026-07-25）

全ページ調査に基づく再構成を実施した。将来の改稿時は、ここに書かれた判断基準を引き継ぐこと。

診断（当時の課題）

  1. 用語の初出順とページ順の逆転 — 旧 nav（MB概要 → MBアニメ → Control Rig）に対し、旧 mb_animation.html が Control Rig 用語を無説明で前提にしていた
  2. 情報密度の不揃い — 旧 mb_animation.html が突出（888行・11セクション・図解ゼロ・1見出しに複数ワークフロー同居）
  3. 消化の区切り・検証可能な達成チェックの不在
  4. 実画面との接続の弱さ・MB 側トラブルシューティング不足

順序の設計判断（最重要・変えるときは要注意）

採用した原則：「概念レベルの全体像は先出し、操作レベルの内容は依存順」

  • 判断基準は「未知用語の保留数」——説明されていない用語を保留したまま読み進めるほど理解に使える容量が削られる。全体→詳細型の学習効果（先行オーガナイザ）が出るのは「全体」が概念レベルに圧縮されているときだけ
  • これを実装したのが mb_overview ⑥「アニメ制作の全体地図」（概念のみ・操作なし）＋ 依存順の nav（CR → アニメ基本 → アニメ実践）
  • この教材は「ソフト起動前に読む」設計なので「読んですぐ試せない」コストは低い。効くのは保留数の方
  • 逆に言えば：ページ順を変えたくなったら「そのページが無説明で前提にする用語は何か」を先に洗い出すこと。概念コンテンツなら前に出してよいが、操作コンテンツを依存元より前に出すと同じ問題が再発する
