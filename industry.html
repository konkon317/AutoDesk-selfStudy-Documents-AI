① パイプラインでの MB の立ち位置

MotionBuilderは、Mocapのデータ処理に特化したミドルウェアです。「最初から最後まで全部MB」という使い方はほぼなく、パイプラインの中継点として機能します。

一般的な Mocap → 最終成果物 のパイプライン

撮影（Mocap Studio） → 生データ（C3D / BVH） → MotionBuilder
修正・リターゲット・編集 → FBX → Maya / Houdini
仕上げ・レンダリング → 最終成果物

ゲームの場合はMayaの後にUnity/Unrealへ。バーチャル系はMBの後にリアルタイムエンジンへ直接。

MBが得意とするのは「Mocapデータを受け取り、人間が使えるアニメーションに変換する」という工程です。Maya単体でもできますが、MBはこの目的に最適化されているため処理速度・直感性で勝ります。

③ 納品形態・ファイル形式まとめ

形式用途特徴
FBX MB → Maya / ゲームエンジン の標準中継 Autodesk製。アニメーション・メッシュ・マテリアルを一括。MBで書き出す主要形式
BVH Mocap生データの保存・交換 骨格+モーションのみ。軽量だがスキンメッシュなし。MBに読み込んでFBXに変換するのが一般的
Alembic (.abc) 頂点アニメーション・クロスシム結果の受け渡し ポリゴン頂点を時系列で保存。ベイク済みメッシュをそのままDCC間で移送する用途
USD 大規模VFX・映画パイプラインの標準化 Pixarが開発。シーン全体を構造化。ゲーム・ゲームエンジン側にも普及中
glTF / GLB ウェブ・メタバース・リアルタイム3D ウェブ標準に近い3Dフォーマット。Unreal/Unityへの流通も増加
💡

MBを使う限りまず覚えるのはFBX： BVHで受け取り→MB処理→FBX書き出しがほぼすべての業界で共通のパターンです。FBXの読み書き設定（軸方向・フレームレート・スケール）は書き出し先ツールに合わせる必要があります。

📝 コラム：MBを「メインツール」と「脇役」で学ぶ場合の違い

MBをメインで使う人（TA・専任アニメーター）は、スクリプト（Python/MoBu API）・パイプライン最適化まで深掘りします。一方、「Mocapを使うシーンで効率的に処理したい」という文脈なら、Characterize → Retarget → Control Rig修正 → Plot → FBX という一本のフローを確実に使えることが最優先です。スクリプトや高度なRetarget設定はその後の選択肢として持てば十分です。

限られた時間でMBを学ぶなら、「どの業界のどの工程」を自分が担当するかを最初に定義しておくと、学習対象がはっきりします。

⑤ MBとMayaの役割分担 — どっちで何をするか

MBとMayaはよく「どちらを使えばいいか」と比較されますが、競合ツールではなく工程分担ツールです。それぞれが得意とする工程が明確に異なり、多くのパイプラインで両方が役割を分けて存在します。

MotionBuilder Maya
一言で Mocap処理の工場（前工程ツール） アニメーション制作のスタジオ（仕上げツール）
強み リターゲット・Floor Contact・Pinningが速い。大量Mocapデータを捌ける。HumanIK専用UIが直感的 Graph Editor・Dope Sheet・タンジェント制御が細かい。リギング全般。カーブの自由度が高い
弱み Dope Sheet が使いにくい。手付けUIはMayaより不便。リギングはほぼできない Mocap大量処理が遅い。HumanIKはあるがMBほど直感的でない
向くアニメーション 写実的なMocapベース。量産Mocap処理 誇張・スタイライズド・ループ・細かい緩急設計
最終成果物 FBX（次工程へ渡す中間ファイル） FBX / Alembic / USD（最終出力に近い）

スタイライズド・ゲームアニメーション（誇張系）の場合
日本のアクションゲームなど誇張表現が強いタイトルでは、MBを使わずMayaまたはエンジン直で手付けするケースも多いです。Mocapをベースとしても、最終的な「緩急・タイミング・スクワッシュ&ストレッチ」はMayaのGraph Editorでカーブを設計するほうが精度が出やすいです。
Mayaに渡すべき判断基準
  • 緩急・タイミングをカーブで細かく設計したいとき
  • ループアニメーションの前後フレームをつなぐとき
  • 誇張表現（オーバーシュート・バウンス・スクワッシュ）が必要なとき
  • 人型以外のオブジェクトのアニメーションを仕上げるとき
